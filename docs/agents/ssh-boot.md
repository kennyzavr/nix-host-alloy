# Runtime SSH keys and initrd files

Read this for key lifecycle and first-installation behavior. Sources:
[ssh.nix](../../modules/core/ssh.nix),
[ssh-keygen.sh](../../modules/core/ssh-keygen.sh), and
[boot.nix](../../modules/core/boot.nix). For VM-specific deployment, read
[QEMU](qemu.md).

`hosts.<host>.ssh.keys.<name>` declares a root-owned SSH key generated by
`alloy-ssh-keygen.service`, even when `ssh.enable = false`. Declaring a key does
not select it for either SSH server: use `ssh.keyPaths` or `boot.ssh.keyPaths`.

- `type`: `ed25519` (default) or `rsa`.
- `bits`: `null` for Ed25519, RSA defaults to 4096 (minimum 2048).
- `path`: defaults to `/var/lib/alloy/ssh/keys/<name>`; keep this on persistent storage.
- `publicKeyPath`: read-only `${path}.pub`.

Names accept letters, digits, underscores and hyphens. Paths must be normalized,
absolute, outside `/nix/store`, and contain only letters, digits, underscores,
dots, hyphens and slashes.

The main-system SSH service requires and starts after the key generator. The
generator uses a lock and temporary files. It preserves existing private keys,
restores missing public keys, and
fails on corrupt keys, mismatched algorithms/sizes, mismatched public keys or
symlink key files. Private keys have mode 0600, public keys 0644, both owned by
root. Removing a declaration does not delete its key. To rotate a key, declare a
new name/path and update consumers; keep old source files while boot generations
still refer to them.

`hosts.<host>.boot.files.<name>.source` is a string naming an existing file on the
**target host**. Its read-only `.path` is `/etc/alloy/boot/files/<name>` inside
initrd. The module uses `boot.initrd.secrets` and requires a bootloader supporting
initrd secrets. It does not read source contents during evaluation or generate
missing files. The existing `boot.facts` API is unchanged.

## Two-stage installation

For the initial installation, declare only the key:

```nix
hosts.machine.ssh.keys.initrd = { };
```

Install and boot the machine without initrd SSH. The first boot must be possible
without remote SSH unlocking (for example, using the console). Check that
`alloy-ssh-keygen.service` succeeded and that the private key exists.

Then add the following to the host submodule, keeping the key declaration:

```nix
hosts.machine = { config, ... }: {
  ssh.keys.initrd = { };
  boot.files.ssh-initrd.source = config.ssh.keys.initrd.path;
  boot.ssh = {
    enable = true;
    port = 2222;
    authKeyFacts = [ "admin-ssh-pubkey" ]; # An existing public-key fact.
    keyPaths = [ config.boot.files.ssh-initrd.path ];
  };
};
```

Run `nixos-rebuild switch`. The next boot uses the copied initrd key. Configure
initrd networking and disk unlocking separately as appropriate for the host.

The source key must exist **before** `nixos-install`, `nixos-rebuild boot` or
`nixos-rebuild switch` installs a boot configuration referring to it. Disabling
only `boot.ssh` does not remove a `boot.files` entry. Adding a new key and its boot
file in a single rebuild is therefore insufficient; first generate the key in
the running system, then enable the boot consumer.

Use a separate key for initrd and the main SSH server: the initrd copy resides
with the boot artifacts and is readable offline if the boot partition is not
encrypted. Runtime generation never refreshes already installed boot artifacts.

## Verification

The repository currently has no checked-in SSH lifecycle test scripts. When
changing the generator, use a disposable host/VM and check: creation with SSH
disabled, unchanged private key on rerun, restoration of a missing `.pub`,
rejection of corrupt keys/algorithm or size changes/mismatched public keys, and
permissions. Syntax checking alone does not cover these behaviors.

On a running host, substitute the declared key name:

```sh
sudo systemctl status alloy-ssh-keygen.service --no-pager
sudo journalctl -u alloy-ssh-keygen.service -b --no-pager
sudo ssh-keygen -y -P '' -f /var/lib/alloy/ssh/keys/initrd
sudo ssh-keygen -lf /var/lib/alloy/ssh/keys/initrd.pub
```

`ssh-keygen -y` derives the public key from the private key. Compare its algorithm
and base64 key material with the saved `.pub` (ignore any comment). Successful
service completion also means the generator checked that relationship. Its
oneshot service normally remains `active (exited)`.

For initrd delivery, first install the boot configuration with an existing source
key, then boot that configuration. Compare the file at `boot.files.<name>.path`
inside initrd with the original on the mounted real root. A file's existence in
the main system alone does not prove that it was included in initrd. Conversely,
rebuilding boot artifacts does not modify the initrd of the currently running
boot. See the [QEMU guide](qemu.md) before testing this in a VM.

If inspecting an archive offline, inspect the installed boot artifact: the
store-built base initrd does not contain host-local secrets appended during
bootloader installation. If testing by SSH, select only the new key for boot SSH
so another configured key cannot mask delivery problems.
